# Synthetic-credential account recovery coordinator

A single-tenant-per-database recovery coordinator for an account-recovery
flow in which two *independent* proofs must agree before an account may
advance to a new credential generation.

Everything in this delivery is synthetic: the signing key, all tenant /
account / channel / proof ids and every profile are invented. No real
credential, secret or personal datum is present anywhere. The program uses
only the Python 3.12 standard library and CPU; it runs fully offline.

---

## 1. Running it

```bash
# deliverable entry point: execute cases.json and write result.json
python -m solution --input cases.json --output result.json

# automated tests
python -m unittest discover -s tests -v

# optional flags
python -m solution --input cases.json --output result.json --no-races
python -m solution --input cases.json --output result.json --workdir .scratch
```

Exit status of `python -m solution`: `0` when every case and race matched its
expectations, `1` when at least one did not, `2` when the input file could not
be read or parsed (`E101`). The result document is always written.

Requirements: Windows (tested natively), CPython 3.12, no third-party
packages, no network access. SQLite comes from the standard library.

### Layout

| path | contents |
| --- | --- |
| `solution/` | the coordinator (see §3) |
| `cases.json` | the reproducible corpus: 27 single-process cases + 8 two-process races |
| `result.json` | the corpus executed once; the record of the run reported in §7 |
| `tests/` | 100 automated tests |
| `tools/` | the independent case generator and the mutation checker |
| `task/PROMPT.txt` | the original task statement |

`cases.json` is generated by `python tools/gen_cases.py cases.json` from
`tools/gen_cases.py` and `tools/races.py`. Both use `tools/synth.py`, which
re-implements the canonical encoding and HMAC rule **without importing
`solution`** — the corpus is an independent statement of the protocol, not a
transcript of the implementation.

## 2. Concepts

```
tenant ── account ──┬── attempt(attempt=1, account_gen=1, profile_digest) ── proofs
                    │        (an attempt is a pending credential change)
                    └── attempt(attempt=2, account_gen=2, profile_digest) ── proofs
```

* **account generation** (`accounts.account_gen`) — an integer that advances by
  exactly one each time a recovery commits. It is the account's credential
  version, and it is what makes a proof "old".
* **attempt** — one pending credential change: an id, the account, the account
  generation it was opened at, a *pending profile digest*, and a validity
  window `[created_at, expires_at]` (both ends inclusive).
* **proof** — a verifier's statement that one channel vouches for one attempt.
  It is bound to the attempt id, account id, account generation, pending
  profile digest, channel and channel generation, and carries its own validity
  window `[not_before, not_after]` (both ends inclusive) and an issuer
  (the verifier).
* **channel** — a human, device or admin channel. Channels have a generation
  that advances on `rotate` and stop working on `revoke`.

### Recovery rule

A submission for attempt *A* succeeds when **all** of the following hold:

1. *A* belongs to the account, is open, and the request time `at` lies in
   `[created_at, expires_at]`;
2. *A* was opened at the account's **current** generation, and no recovery has
   already advanced that generation;
3. there is a pair of proofs `(p, q)`, `p.id < q.id`, that are both
   `available`, correctly signed, inside their own windows, and bound to *A*'s
   attempt, account, account generation and profile digest;
4. both use channels that are live at their **current** generation;
5. the pair has two different channels, two different channel types, two
   different issuers, and at least one of the two types is `human` or `admin`;
6. `(p, q)` is the lexicographically smallest valid pair ordered by
   `(p.id, q.id)` — so storage order and enumeration order never change the
   result.

A pair that fails only rule 5 (`E203`, `E207`, `E208`, `E209`) is reported as
`E506` with `pair_codes` naming every pair rule that was broken.

### The commit

One SQLite transaction performs exactly five effects, or none:

1. `p` and `q` are marked `consumed` (with `consumed_by`, `consumed_at`);
2. `accounts.account_gen` advances by one;
3. every still-open attempt **of the consumed generation** is closed with
   `closed_by = "recovery:<recovery digest>"`;
4. a `recoveries` row is inserted for the new generation;
5. the request receipt is persisted in `ops`.

Because a rollback is atomic, a crash anywhere before `COMMIT` leaves *every*
one of those untouched.

## 3. Source map

| module | responsibility |
| --- | --- |
| `solution/model.py` | canonical JSON, profile/attempt/recovery digests, HMAC rules, case-file validation |
| `solution/db.py` | schema, immutable state views, snapshot reads, `WriteTx` |
| `solution/engine.py` | evaluation, pair selection, commit, channel lifecycle, idempotency |
| `solution/errors.py` | the stable error-code catalogue |
| `solution/syncpoints.py` | file-based synchronisation points between processes |
| `solution/worker.py` | one independent process executing one request file |
| `solution/runner.py` | case/race executor, expectation checking, CLI |

### Concurrency design

* SQLite runs in WAL mode with `busy_timeout`; two processes may read while
  one writes.
* Every decision is made **inside** `BEGIN IMMEDIATE`: the transaction takes
  the write lock first, then re-reads the whole tenant. A preview taken
  earlier is advisory and never trusted at commit time. A revocation or a
  competing recovery that lands first is therefore seen by the loser, which
  rejects instead of overwriting it.
* Writes are serialised by SQLite itself; the loser re-reads committed state.
  There is no optimistic version check to get wrong.
* The commit is a single transaction, so two attempts of one account cannot
  both win.

### Synchronisation points

`solution/syncpoints.py` implements a rendezvous over marker files:

* the worker writes `<point>__<token>.arrived` and fsyncs, then polls for
  `<point>__<token>.released`;
* the controller waits for `arrived` and later creates `released`.

The engine calls `sync.hit(point)` and knows nothing else about the harness.
Points are:

| point | emitted |
| --- | --- |
| `recovery.before_lock` | before the write lock is taken |
| `recovery.after_consume` | inside the transaction, after both proofs were consumed |
| `recovery.after_write` | after the receipt was written, still inside the transaction |
| `recovery.after_commit` | after `COMMIT`, before the result is returned |
| `channel.before_lock` / `channel.after_write` / `channel.after_commit` | the same for lifecycle requests |

A worker parks only at the points named in its `park` list, so an unexpected
point can never hang it. The tests fix every interleaving explicitly; no test
relies on `sleep` or on which process happens to be faster.

The harness starts processes with `subprocess.Popen` and kills **only those
handles**. It never enumerates the process table. A dedicated test starts an
unrelated decoy process and asserts it survives a race that kills a worker.

## 4. Input format

`cases.json` (schema `recovery-cases/1`):

```jsonc
{
  "schema": "recovery-cases/1",
  "description": "...",
  "cases": [ { case }, ... ],
  "races": [ { race }, ... ]
}
```

A tenant may be described **exactly once in the whole file** (across cases and
races); a duplicate is a file-level `E103` and nothing runs.

### 4.1 Case

```jsonc
{
  "case_id": "bounds",
  "tenant": "tenant-bounds",
  "account_id": "acct-1",          // account under test
  "signing_key": "synthetic-recovery-key-2026",
  "load": {
    "now": 0,                      // default request time when a request omits "at"
    "channels": [{"id": "h", "type": "human"}, {"id": "d", "type": "device"}],
    "accounts": [{"id": "acct-1", "account_gen": 1, "status": "active"}],
    "attempts": [{
      "id": "att-1", "account_id": "acct-1", "account_gen": 1,
      "profile": {"display_name": "alice", "email": "alice@example.test"},
      "created_at": 100, "expires_at": 900, "status": "open"
    }],
    "proofs": [{
      "id": "p-01-human", "attempt_id": "att-1", "account_id": "acct-1",
      "account_gen": 1, "profile_digest": "<sha256 of canonical profile>",
      "channel_id": "h", "channel_type": "human", "channel_gen": 1,
      "not_before": 100, "not_after": 900,
      "issuer": "v-human", "signature": "<hex hmac>",
      "status": "available"                 // optional; "consumed" needs consumed_by/consumed_at
    }],
    "channel_events": [{"id": "ev-1", "channel_id": "h", "kind": "rotate",
                        "channel_gen": 2, "at": 300, "signature": "<hex hmac>"}]
  },
  "operations": [ ... ],
  "expect": {
    "outcomes": [ {"op": 0, "status": "ok", "candidate": ["p-01-human", "p-02-device"]} ],
    "final":    { "accounts.acct-1.account_gen": 2 }
  }
}
```

Channel ids and types are declared once and never change; a proof repeating a
channel with a different type is a load error (`E104`). This is why there is
no runtime "channel type mismatch" code: the invariant is established at load
time and cannot be violated afterwards. Records of other accounts in the same
tenant are allowed (attempts, proofs and channels share a tenant namespace).

### 4.2 Operations

| `op` | required fields | effect |
| --- | --- | --- |
| `request_recovery` | `account_id`, `attempt_id` | validate a pair and commit atomically |
| `preview` | `account_id`, `attempt_id` | read-only view of usable proofs and the chosen pair |
| `rotate_channel` | `channel_id`, `channel_gen`, `signature`, `at` | advance a channel generation |
| `revoke_channel` | `channel_id`, `channel_gen`, `signature`, `at` | kill a channel |
| `get_account` | `account_id` | account, attempts, recovery rows |
| `get_attempt` | `attempt_id` | attempt and its proofs |
| `get_recovery` | `account_id` | recovery rows of an account |
| `get_state` | — | the whole tenant snapshot |

All operations accept `remote_id` (required, unique *within its purpose*) and
optional `at` (request time; defaults to `load.now`).

`request_recovery`, `rotate_channel` and `revoke_channel` take a **request
receipt**: the first execution's result is persisted in the same transaction
as its effects, and repeating the same `remote_id` with identical parameters
returns that exact receipt with `"replayed": true`. Repeating it with
different parameters is refused with `E501` and leaves the stored receipt
untouched.

### 4.3 Signature rules

Canonical JSON is UTF-8, keys sorted, no whitespace (non-ASCII is **not**
escaped). `signature = HMAC-SHA256(key, canonical_json(payload))`, hex.

* proof payload: `id, attempt_id, account_id, account_gen, profile_digest,
  channel_id, channel_type, channel_gen, not_before, not_after, issuer`
* channel event payload: `id, channel_id, kind, channel_gen, at`
* lifecycle request payload: `id (= remote_id), channel_id, kind, channel_gen,
  at`

The same rule signs seeded events and lifecycle requests, so one key
authenticates both.

## 5. Error codes

Business failures are persisted in the receipt of the request that caused
them and are **fixed**: a repeat of that `remote_id` with the same parameters
returns the stored failure even if the state has since become recoverable.
Infrastructure failures (`E6xx`, `E7xx`) are never persisted.

| code | meaning | persisted |
| --- | --- | --- |
| `E100` | request is structurally invalid | no |
| `E101` | cases file is unreadable / not JSON | no (whole run) |
| `E102` | unknown operation name | no |
| `E103` | duplicate tenant in the file, or duplicate record id in a case | no (whole run) |
| `E104` | loaded record is malformed | no (that case) |
| `E201` | referenced account/attempt does not exist in this tenant | yes |
| `E203` | both proofs share one verifier | yes (pair code) |
| `E204` | proof is past `not_after` | yes (per-proof) |
| `E205` | proof is bound to another attempt/account/generation/profile | yes (per-proof) |
| `E206` | proof is already consumed | yes (per-proof) |
| `E207` | both proofs come from one channel | yes (pair code) |
| `E208` | both proofs have one channel type | yes (pair code) |
| `E209` | neither proof is `human` or `admin` | yes (pair code) |
| `E210` | proof is before `not_before` | yes (per-proof) |
| `E211` | attempt is past `expires_at` | yes |
| `E212` | account is frozen | yes |
| `E213` | attempt starts after the request time | yes |
| `E214` | a lifecycle event cannot precede an existing one | yes |
| `E301` | a signature does not verify | yes (proof, event or case load) |
| `E401` | channel is unknown in this tenant | yes |
| `E402` | channel was revoked | yes |
| `E403` | proof carries an old channel generation | yes (per-proof) |
| `E404` | lifecycle request names a generation that is not the next one | yes |
| `E501` | request id reused with different parameters | no (refusal, receipt kept) |
| `E502` | attempt belongs to a different account | yes |
| `E503` | attempt was opened at an older account generation | yes |
| `E504` | attempt is closed | yes |
| `E505` | a recovery already happened at this attempt's generation | yes |
| `E506` | no valid proof pair (details in `reasons` / `pair_codes`) | yes |
| `E602` | database stayed locked past the busy timeout | no, retryable |
| `E701` | a synchronisation point timed out | no |
| `E799` | unexpected internal/platform failure | no |

`E506` is the aggregate "cannot recover with what is on offer"; the receipt
then carries `reasons` (one entry per proof, in proof-id order) and
`pair_codes` (the union of pair rules broken by any possible pair).

## 6. Boundary examples (all from `cases.json`)

| situation | expectation | case |
| --- | --- | --- |
| request `at == proof.not_before` | accepted | `bounds` op 0 |
| request `at == proof.not_after` | accepted | `bounds` op 6 |
| request `at == attempt.expires_at` | accepted | `bounds` op 2 |
| request `at == attempt.created_at` | accepted | `startbound` op 1 |
| one tick past any of those | rejected (`E204`/`E210`/`E211`/`E213`) | `bounds`, `startbound` |
| recovery at attempt generation *g* | advances account to *g+1*, closes **all** open attempts of *g* | `second`, `bounds` |
| attempt opened at generation 2 while account is at 1 | accepted once the account advances | `second` op 2 |
| attempt opened at an older generation | `E503` | `stalegen` |
| pair `(a, k)` forbidden, `(a, m)` legal | `(a, m)` chosen even when `(k, m)` exists | `lexi` |
| ids `"p-10"` and `"p-9"` | `"p-10"` sorts first (string order) | `numids` |
| channel rotated after the proof was issued | `E403` (stale generation) | `chanlife`, `newgen` |
| channel revoked after the proof was issued | `E402` | `chanlife` |
| request time *before* a revocation | still `E402`: lifecycle state is committed state | `chanlife` op 1 |
| failure persisted, state later recoverable | same `remote_id` replays the failure; a new id succeeds | `fixedfail` |
| same `remote_id` in two tenants | two independent receipts | `scope`, `scopeb` |

## 7. Measured results

Environment: Windows 11 Pro `10.0.26200`, CPython `3.12.8`, SQLite `3.45.3`,
CPU only.

```
python -m solution --input cases.json --output result.json
  cases: 27   cases_ok: 27   cases_failed: 0
  races:  8   races_ok:  8   races_failed: 0
  exit status 0

python -m unittest discover -s tests -v
  Ran 100 tests in ~36 s
  OK

python tools/mutation_check.py
  all 20 behavioural mutants were caught
  2 further mutants broke a guard invariant (reported separately)
```

Corpus coverage: 81 executed operations — 20 commits, 23 business
rejections, 3 verified replays. Every business error code in §5 appears as an
expectation somewhere in `cases.json`.

Three consecutive full runs produced byte-identical result documents (apart
from worker stdout fields, which the test strips).

### How the expectations were obtained

No expected value is derived from the implementation.

* The corpus generator (`tools/gen_cases.py`, `tools/races.py`) writes every
  expectation by hand from the rules in §2 and computes signatures with
  `tools/synth.py`, an independent re-implementation of the documented HMAC
  rule. `tools/synth.py` never imports `solution`.
* `tests/test_rules.py` asserts individual rules directly (boundary values,
  pair ordering, channel-generation maths) without going through a case file.
* `tools/mutation_check.py` proves the corpus is *sensitive*: it applies 22
  single-rule mutations to a copy of `solution/`, runs the corpus and the rule
  tests against each, and requires every mutant to be caught. This is what
  caught, for example, that an arbitrary pair ordering and a missing
  "different verifier" rule were initially not pinned by any assertion.

## 8. Two-process races

| race | ordering | expected outcome |
| --- | --- | --- |
| `race-revoke-first` | W1 previews and parks; W2 revokes the device channel; W1 resumes | W2 commits, W1 rejects `E506`, account generation stays 1 |
| `race-two-attempts` | both attempts see the same valid state, W1 commits first | W1 commits; W2 rejects `E505`; `att-2` stays open but is closed by the commit |
| `race-expiry-boundary` | W1 at `not_after + 1` runs first, then W2 exactly at `not_after` | W1 rejects `E506`; W2 commits |
| `race-expiry-after-commit` | recovery commits, then a fresh attempt at the new generation | both commit, generation 2 → 3 |
| `race-kill-before-commit` | W1 parked after consuming both proofs inside its transaction, then killed | independent readers see the old state; retry commits, then replays |
| `race-kill-before-reply` | W1 parked after `COMMIT`, then killed | committed state is intact; retry replays the stored receipt |
| `race-failed-then-revoke` | a failing request, then a revocation, then replays | the stored failure is returned for the same id; a new id re-evaluates |
| `race-same-request-id` | two workers use one request id concurrently | one commits, the other replays its receipt |

The kill races compare *recovery snapshots* (accounts, attempts, proofs,
channel events, recovery rows, receipts) taken before, during and after the
kill, so a partially applied commit cannot pass unnoticed.
